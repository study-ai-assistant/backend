# Контракт API

## Подход «сначала контракт» (API-first)

Мы сначала описываем и согласовываем API, а потом пишем код. Так команды backend и mobile могут работать параллельно:

1. **Backend предлагает** изменение контракта: правит [`openapi.yaml`](openapi.yaml) в отдельной ветке и открывает Pull Request.
2. **Mobile проверяет**: хватает ли данных для экранов, понятны ли поля и ошибки. Минимум один участник из mobile ставит approve.
3. После слияния контракт считается **согласованным**. Backend реализует эндпоинты, mobile пишет клиент (можно на заглушках по контракту, не дожидаясь сервера).
4. Любое изменение уже согласованного контракта — только через новый PR с review от mobile.

Правило: код сервера и клиента должен соответствовать `openapi.yaml`. Если они расходятся — правим код или контракт через PR, а не «договариваемся в чате».

## Формат

Контракт ведётся в формате [OpenAPI](https://spec.openapis.org/oas/v3.1.1.html) 3.1 в файле [`openapi.yaml`](openapi.yaml).

Посмотреть контракт в удобном виде:

- вставить содержимое файла в [Swagger Editor](https://editor.swagger.io/);
- или открыть файл в IDE с плагином OpenAPI.

## Что описывать для каждого эндпоинта

- путь и метод;
- краткое описание (`summary`) на русском;
- параметры и тело запроса с примерами;
- ответы: успешный и ошибки (400, 413, 502 и т. д.) с примерами;
- ограничения (максимальный размер текста, поддерживаемые форматы файлов).

## Режимы обработки

Сервер поддерживает режимы, перечисленные в описании `openapi.yaml`. Точные идентификаторы режимов (`summary_short` и т. п.) — ЗАПОЛНИТЬ при согласовании черновика контракта в Спринте 1.
