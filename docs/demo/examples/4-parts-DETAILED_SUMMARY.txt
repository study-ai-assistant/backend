Инвариант — условие, которое должно сохраняться программой до и после выполнения операции (например, уникальность идентификаторов, неотрицательное количество). Проверка инварианта относится к границе изменения данных; при её нарушении операция завершается ошибкой без частичного изменения состояния.

Пустая коллекция допускается, если её контракт не запрещает. Размер входных данных ограничивается для избежания дорогостоящих вычислений. Пример ограничения: 12 запросов / мин при лимите 10 → отказ (код 429) или помещение в очередь.

Тестовые наборы из 20 элементов (или 40, 60, 80 в зависимости от контекста) проверяют:
- пустой ввод,
- один элемент,
- полный набор.

При ошибке на определённом шаге проверяется отсутствие результата и освобождение ресурсов. Сам вызов функции не доказывает корректность данных; необходимо сравнивать вход, контракт и наблюдаемый результат. Названия режимов и числовые значения должны совпадать, округление, меняющее смысл, недопустимо.

Время обработки части = 3‑6 сек; общее время = количество частей × время части. Ожидание квоты и объединение результатов учитываются отдельно и не включаются в обещание скорости сервиса.

Коды ошибок
- 400 — неверный запрос / нарушение инварианта, указание некорректных полей.
- 429 — превышение лимита запросов, сообщение о перегрузке.
- 413 — превышен допустимый размер.
- 404 — ресурс не найден.
- 202 — задание принято, результат ещё не готов; клиент опрашивает URL из заголовка Location (может быть указан Retry-After).

Отказы
1. Превышение лимита → коды 429 (HTTP) или специфический код отказа; клиент получает рекомендацию повторить запрос позже.
2. Нарушение инварианта / некорректный ввод → код 400 с указанием полей, которые нужно исправить.

Повторные попытки
Клиенту нужны:
- идентификатор задания (если есть),
- код ошибки,
- рекомендация (уменьшить нагрузку, ждать указанный интервал, исправить параметры).

Граничные тесты
Проверяются значения: максимум, максимум − 1, максимум + 1. При повторных запросах с одинаковыми параметрами ожидается одинаковый код отказа.

Согласованность при конкуренции
Число завершённых частей должно быть ≤ общего числа частей. После перезапуска памяти все временные данные очищаются; клиент может потребовать повторную отправку запроса. Свойства временного хранения следует описать в контракте.

Очереди и фоновые задания
- Задания помещаются в очередь в порядке поступления, один исполнитель обрабатывает их последовательно.
- Клиент получает идентификатор и проверяет статус: *в очереди*, *выполняется*, *готово*, *ошибка*.
- Прогресс измеряется в процентах завершённых частей, а не в оценке времени.
- При ошибке итоговый результат не выдаётся.

Ограничения нагрузки
Пример: 48 запросов / мин при лимите 40 → 8 запросов отклоняются или помещаются в ограниченную очередь; клиент получает отказ с соответствующим кодом.

HTTP‑протокол
- GET — чтение ресурса.
- POST — создание ресурса или запуск действия.
- 202 — задание принято, результат будет готов позже.
- 200 — успешный запрос с готовым результатом.
- 400, 413, 404, 429 — типичные коды отказов.

Общие требования перед запуском
- Проверка пред‑условий (например, сортировка для бинарного поиска, соблюдение квот).
- Убедиться, что входные данные соответствуют контракту.

Успешный исход
- Запрос выполнен, возвращён итоговый результат (код 200/202). 

Эти правила применимы ко всем рассмотренным сценариям: поиску (линейный, бинарный), обработке запросов, очередям и фоновым заданиям, а также HTTP‑интеракциям.
