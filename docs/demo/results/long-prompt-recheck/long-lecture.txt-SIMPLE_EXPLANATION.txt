Инварианты и проверка условий
Инвариант — правило, которое должно оставаться истинным до и после любой операции программы. Примеры: у каждого заказа уникальный идентификатор, количество элементов неотрицательно. При нарушении инварианта операция завершается ошибкой и не меняет состояние системы.

Граничные случаи входных данных
Пустая коллекция считается допустимой, если её не запрещает контракт. Размер входа ограничивают, чтобы избежать дорогих вычислений. При превышении лимита запросов (например, 12 запросов / мин при ограничении 10) сервер обязан вернуть отказ или поставить запросы в очередь, а не просто «потерять» их.

Тестирование граничных случаев
Для набора из N элементов проверяют три варианта: пустой ввод, один элемент, полный набор. Если ошибка проявляется на каком‑то шаге, тест подтверждает отсутствие результата и освобождение ресурсов. Граничные проверки включают значение‑1, значение и значение + 1; превышение лимита должно возвращать одинаковый код ошибки при повторных попытках.

Время работы и расчёты
Если одна часть обрабатывается T секунд, k последовательных частей займут k·T секунд; ожидание квоты и объединение считаются отдельно. Такие расчёты приводятся лишь как пример, а не как гарантированная скорость сервиса.

Контракт и наблюдаемый результат
Названия режимов в запросе и ответе должны совпадать. Числовые параметры нельзя округлять так, чтобы изменился смысл условия. Если в источнике нет определения, его нельзя придумывать.

Согласованность при конкурентном доступе
Несколько клиентов, читающих одно и то же состояние, должны видеть одинаковые поля (например, число завершённых частей ≤ общее число). После перезапуска памяти состояние очищается, поэтому клиент может потребоваться повторно отправить запрос.

Линейный и бинарный поиск
Линейный поиск перебирает элементы последовательно; в худшем случае требуется n сравнений для n элементов. Бинарный поиск работает только с отсортированными данными, каждый шаг делит диапазон пополам, что даёт существенно меньше сравнений. Без предварительной сортировки бинарный поиск может вернуть неверный результат.

Оценка сложности
Запись O(n) показывает, как растут затраты при увеличении входа, а не конкретное время выполнения. Реальные измерения в миллисекундах или секундах нужны лишь как дополнение к асимптотическому анализу.

Ограничения и отказ запросов
Если сервер способен обработать L запросов в минуту, лишние запросы должны быть явно отклонены (код 429 или другой соответствующий) или помещены в ограниченную очередь; их нельзя просто «проглотить». Числа в условиях нельзя округлять так, чтобы менялось требование задачи.

Очередь заданий
Очередь хранит задания в порядке их поступления. Один исполнитель берёт следующее задание только после завершения текущего. Клиент получает идентификатор задания и отдельно проверяет его статус. Состояния задания: в очереди, выполняется, готово, ошибка. При ошибке окончательный ответ не выдаётся (нельзя отдавать частичный результат). Прогресс показывает количество уже завершённых частей, а не предполагаемое время окончания.

Отказ и повторные попытки
Два типа отказов: превышение квоты — сервер возвращает код отказа и сообщение; ошибка обработки на каком‑то шаге — сообщение об ошибке без раскрытия конфиденциальных данных. Для повторной попытки клиенту нужны ID задания, код отказа и рекомендация (например, «снизьте частоту запросов» или «исправьте входные данные»).

Методы запросов HTTP
GET — только чтение ресурса, без изменения состояния.
POST — создание ресурса или запуск действия; может вернуть код 202 (задание принято, результат ещё не готов). Клиент затем опрашивает адрес из заголовка Location.

Коды ошибок
400 — неверно сформированный запрос.
413 — превышён допустимый размер данных.
404 — ресурс не найден.
При сбое внешнего сервиса следует вернуть понятное сообщение, а не скрывать ошибку.

Тестирование и граничные случаи в API
Проверяются пустой набор, один элемент и полный набор. При ошибке на конкретном шаге проверяется отсутствие конечного результата и освобождение ресурсов. Граничные значения (максимум, максимум‑1, максимум + 1) должны вести себя одинаково, возвращая один и тот же код отказа.

Время обработки в сервисе
Одна часть может занимать, например, 6 секунд; четыре части подряд — 24 секунды. Ожидание квоты и объединение считаются отдельно; это лишь пример расчёта, а не гарантия скорости.

Поведение клиента при повторных запросах
Повторный POST может создать новое задание. После перезапуска сервера память очищается, поэтому клиент может потребовать повторную отправку данных. Ответ сервера подтверждает выполнение конкретного запроса, но не исключает ошибок в других запросах.
