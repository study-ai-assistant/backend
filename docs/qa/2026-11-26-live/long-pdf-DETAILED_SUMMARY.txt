Часть 1 – Данные и инварианты  
Инвариант — условие, сохраняемое до и после операции (например, уникальность идентификаторов, неотрицательное количество). При его нарушении операция завершается ошибкой без частичного изменения состояния. Пустая коллекция допускается, если контракт её не запрещает. Размер входа ограничивается из‑за дорогих вычислений (пример — 12 запросов/мин, лимит 10 → отказ или очередь). Тесты покрывают пустой ввод, один элемент и полный набор; при ошибке на конкретном шаге проверяется отсутствие результата и освобождение ресурсов. Время обработки части = 3 с → четырёхчастный процесс = 12 с (без учёта ожиданий и объединения). Название режима должно совпадать в запросе и ответе; числовые значения нельзя округлять так, чтобы менялся смысл. При ошибке не раскрывать содержимое документа и секретные настройки. Граничные проверки: максимум, максимум‑1, максимум + 1; превышение лимита возвращает одинаковый код при повторе. При одновременном чтении клиентами состояние должно быть согласовано; после перезапуска память очищается, требуется повторная отправка. Успешный ответ подтверждает только конкретный запрос, не доказывая отсутствие ошибок в остальных документах.  

Линейный поиск сравнивает элементы последовательно, худший случай = n сравнений → O(n). Бинарный поиск делит отсортированный диапазон пополам; обязательна предварительная сортировка. Оценка сложности O(n) применяется к учебному примеру проекта.  

Часть 2 – Очереди и фоновые задания  
Очередь хранит задания в порядке поступления; один исполнитель берёт следующее только после завершения текущего. Клиент получает идентификатор задания и проверяет его статус независимо. Состояния задания: в очереди, выполняется, готово, ошибка — каждое имеет отдельное значение. Прогресс отображает количество завершённых частей, а не предполагаемое время выполнения. При ошибке части нельзя выдавать неполный итоговый ответ. Временное хранение результатов ограничено сроком; после перезапуска память очищается, клиент может потребовать повторную отправку.  

Пример 3: сервер принимает 36 запросов/мин, при лимите 30 лишние 6 запросов отклоняются с сообщением или помещаются в ограниченную очередь.  

Тесты наборов из 60 элементов проверяют пустой ввод, один элемент, полный набор; при ошибке на шаге 4 проверяется отсутствие итогового результата.  

Все измерения (пиковая память, число вызовов, длительность) фиксируются отдельно и не заменяют оценку качества ответа.  

Часть 3 – Освобождение ресурсов и HTTP‑протокол  
Вызов функции ≠ доказательство корректности данных. Время обработки части фиксировано (пример — 5 с или 6 с); чистое время = количество частей × время части; ожидание квоты и объединение считаются отдельно. При ревью сравниваются вход, контракт и наблюдаемый результат; название режима должно совпадать в запросе и ответе. Числа нельзя округлять так, чтобы менялся смысл условия. При отсутствии определения в источнике модель не добавляет догадки.  

Перед запуском проверяется валидность входных данных (соответствие контракту). Успешный исход — завершение задания с итоговым результатом. Отказы — превышение лимита или неверный запрос. При ошибке клиент получает код, описание причины и рекомендацию (изменить размер запроса, подождать).  

HTTP‑коды: GET — чтение, POST — создание/запуск. 202 — задание принято, результат ещё не готов; клиент получает адрес из заголовка Location и опрашивает с интервалом. 400 — неправильный запрос; 413 — превышен размер; 404 — ресурс не найден. Ошибка внешнего сервиса должна быть ясным сообщением; повторный POST может создать дублирующее задание.  

Лимиты запросов: пример — 48 запросов/мин при лимите 40 → 8 запросов отклоняются или попадают в очередь, а не исчезают.  

Тесты наборов (пустой ввод, один элемент, полный набор) при ошибке на шаге 5 проверяют отсутствие итогового результата и освобождение ресурсов. Повторный запуск очищает память; клиент может потребовать повторную отправку, что следует объявить заранее. Успешный ответ подтверждает выполнение конкретного запроса, но не гарантирует отсутствие ошибок в других документах; полная проверка сравнивает определения и вычисления с исходным материалом, фиксирует ограничения и способ их воспроизведения.  

Часть 4 – Проверка перед началом работы  
Необходимо убедиться, что материал полностью помещается в лимит (размер, количество частей). Успешный исход — сервер возвращает итоговое сообщение, число завершённых частей ≤ общее число. Отказы: а) превышение лимита → одинаковый код ошибки при повторе; б) конфликт чтения → несогласованные поля. Для повторной попытки клиент получает код ошибки, текущий размер/кол‑во частей, требуемые настройки. При повторе эксперимент следует выполнять с теми же данными; изменение настроек помечается явно. Граничные проверки: максимум, максимум‑1, максимум + 1. После перезапуска память очищается, клиент обязан повторно отправить материал; это свойство временного хранилища следует объяснить заранее.  

Часть 5 – Тестирование и измерения  
Перед тестом задаётся известный набор входов и ожидаемый результат; при необходимости используется заглушка внешнего сервиса. Успешный результат — подтверждение выполнения запроса, корректный порядок в очереди, обновлённый прогресс. Отказы: а) превышение квоты → сообщение об отказе; б) ошибка на шаге 6 → отсутствие итогового результата и освобождение ресурсов. Для повторной попытки клиент получает код ошибки и информацию о требуемой очереди/лимите. При измерении времени фиксируются условия эксперимента (очередь, внешние лимиты); один замер не гарантирует одинаковую скорость. Пример чистого времени: 4 части × 7 сек = 28 сек; ожидание квоты учитывается отдельно. Проверка включает сопоставление входа, контракта и ответа; названия режимов должны совпадать, числовые значения не округляются так, чтобы изменился смысл.  

Часть 6 – Безопасность и ресурсы  
Секретный ключ хранится только на сервере, не попадает в приложение, Git или логи. Внешний ответ не копируется полностью в сообщение об ошибке. Ограничения: размер файла (защита памяти), таймаут (длительность разбора), лимит количества заданий. При превышении лимита запросы отклоняются или помещаются в очередь; сервер сообщает об отказе. Временные файлы удаляются после завершения или ошибки. Пример: 72 запроса/мин, лимит 60 → 12 запросов отклоняются. Тестируются пустой вход, один элемент, полный набор; при ошибке проверяется отсутствие результата и освобождение ресурсов. Время обработки части = 8 сек; 4 части = 32 сек (чистое время, без ожиданий квоты). При проверке название режима должно совпадать в запросе и ответе; числовые значения нельзя округлять так, чтобы менялся смысл условия. Перед началом работы проверяется условие доступа к ресурсу (наличие ключа). Успешный исход — выполнение запроса; отказы — превышение лимита, отсутствие доступа. Клиент получает код ошибки и инструкцию для повторной попытки без раскрытия содержимого документа или секретных настроек.  

Часть 7 – Пример 6 (согласованные поля)  
Требуемые согласованные поля: число завершённых частей ≤ общее число частей; успешное задание — наличие итогового результата. При перезапуске сервера память очищается, клиент может потребовать повторную отправку данных; это особенность выбранного временного хранилища, её нужно объявить заранее. Успешный ответ сервера подтверждает выполнение конкретного запроса, но не гарантирует отсутствие ошибок в других документах. Для полной проверки необходимо сравнить определения и вычисления с исходным материалом, зафиксировать ограничения и способ их воспроизведения. Пример относится к учебному проекту, использует синтетические данные.
