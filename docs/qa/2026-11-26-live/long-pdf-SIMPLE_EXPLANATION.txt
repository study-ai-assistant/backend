Инварианты и проверка границ  

Инвариант — условие, которое должно оставаться истинным до и после выполнения операции (например, уникальность идентификаторов или неотрицательное количество). При его нарушении операция завершается ошибкой без частичного изменения состояния.

Пустая коллекция считается допустимым вводом, если контракт не запрещает её. Размер входных данных ограничивается заранее известным максимумом, чтобы избежать дорогостоящих вычислений. При превышении лимита запрос отклоняется явно (ошибка или постановка в отдельную очередь) и не теряется.

Тесты обычно покрывают три граничных случая: пустой набор, набор из одного элемента и набор с максимальным размером. При ошибке проверяется отсутствие результата и корректное освобождение ресурсов.

Поиск и его сложность  

Линейный поиск сравнивает элементы последовательно; в худшем случае требует ≈ n сравнений, его сложность — O(n).  

Бинарный поиск работает только на отсортированных данных, деля диапазон пополам; без предварительной сортировки результат будет неверным.

Очередь заданий  

Очередь — список задач, приходящих к серверу в порядке отправки. Один исполнитель (worker) берёт первое задание, обрабатывает его, затем берёт следующее. Пока задание не выполнено, клиент получает только его идентификатор и может запросить статус.

Состояния задания:  

- в очереди — ещё не запущено;  
- выполняется — обрабатывается;  
- готово — успешно завершено, результат доступен;  
- ошибка — сбой, результат недоступен.

Прогресс показывает, сколько частей задания уже выполнено, а не предполагаемое время завершения. При ошибке нельзя отдавать частичный результат как окончательный.

Если количество входящих запросов превышает лимит (например, 30 вместо 36), лишние запросы должны получить отказ или попасть в ограниченную очередь; их нельзя «тихо» терять.

Управление ресурсами и повторные попытки  

Перед запуском обработки необходимо проверить, что входные данные соответствуют контракту: правильный формат, допустимый диапазон, известный размер и наличие обязательных полей.

Критерии успеха: запрос принят, сервер возвращает подтверждающий код (например 202) и, при необходимости, адрес для последующего опроса.  

Отказы:  

- 400 Bad Request — ошибка в запросе (неправный формат, отсутствие обязательных параметров, значение выходит за допустимый диапазон, например на 1 больше максимума);  
- 413/429 — превышение лимита размера данных или количества запросов; сервер сообщает, что необходимо уменьшить объём или подождать.

При отказе клиенту должна быть предоставлена информация, необходимая для повторной попытки: код ошибки, краткое описание проблемы, какие параметры скорректировать и актуальные лимиты (максимальный размер, квота запросов). При необходимости также передаётся идентификатор запроса для восстановления состояния.

После завершения обработки или перезапуска сервера все временно хранимые данные очищаются, поэтому клиент может потребовать повторную отправку недостающих частей.

Измерения и граничные тесты  

Пиковая память, количество вызовов и время измеряются отдельно и не заменяют общую оценку ответа. При тестировании берут три граничных значения: максимум, максимум ‑ 1 и максимум + 1. Все они должны пройти; иначе считается ошибкой.

Если материал превышает лимит, сервер каждый раз возвращает один и тот же код ошибки (например 429). Нельзя полагаться только на «средний» пример как корректный для всех входов.

Согласованность при одновременном доступе  

Два клиента, читающие один и тот же пример, должны видеть одинаковые поля: количество завершённых частей ≤ общее количество, а успешный запрос содержит итоговый результат.

Безопасность  

Секретный ключ хранится только на сервере и не попадает в приложение, репозиторий или логи. Ответы не должны включать полный внешний документ. Ограничения по размеру файла и таймауту защищают память и процессор.

Ресурсы  

Временные файлы удаляются после завершения или ошибки. При превышении количества запросов (например, 72 вместо 60 в минуту) сервер должен вернуть отказ или поставить их в очередь, а не просто «потерять».

Порядок проверки  

1. Убедиться, что вход соответствует требованиям (не пустой, не превышает размер).  
2. При успехе вернуть результат и подтверждение выполненного запроса (например 200 с полем «result»).  
3. При отказе сообщить код ошибки и сведения, необходимые для повторной попытки, без раскрытия секретных данных.  

Эти правила применимы ко всем описанным сценариям независимо от конкретных чисел или примеров.
