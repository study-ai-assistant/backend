Инварианты – условия, которые должны оставаться истинными до и после любой операции.  
Примеры: каждый идентификатор заказа уникален, количество товаров не может быть отрицательным. При нарушении инварианта операция завершается ошибкой и не меняет состояние системы.

Пустой ввод считается допустимым, если контракт его не запрещает. Размер входных данных ограничивается (например, сервер обрабатывает не более 10 запросов в минуту); запросы, превышающие лимит, должны получать отказ или помещаться в очередь, а не обрабатываться частично.

Тестирование граничных случаев включает проверку:
- пустого набора,
- набора из одного элемента,
- полного набора.  

При ошибке на определённом шаге тест проверяет, что окончательного результата нет и ресурсы освобождены. Граничные значения проверяют максимум, максимум − 1 и максимум + 1; при превышении лимита все эти варианты должны возвращать один и тот же код отказа.

Время выполнения считается суммой длительностей реальных частей обработки; ожидание квоты и объединение считаются отдельно и не являются обещанием скорости сервиса.

Контракт и ответы  
- Наименования режимов в запросе и ответе должны совпадать.  
- Числовые значения нельзя округлять так, чтобы менялся смысл условия.  
- При ошибке клиент получает только код ошибки и минимум информации, необходимой для повторной попытки (например, текущий лимит, требуемый формат); содержимое документа или секреты не раскрываются.

Конкурентный доступ  
- Несколько клиентов, читающих одно состояние, должны видеть согласованные поля (например, число завершённых частей ≤ общее число частей).  
- После перезапуска памяти состояние очищается, поэтому клиент может потребовать повторную отправку задания.

Измерения (пиковая память, количество вызовов, длительность) рассматриваются отдельно от асимптотической оценки O‑нотации; они не заменяют оценку качества ответа.

Поиск  
- Линейный поиск перебирает элементы последовательно; в худшем случае требует n сравнений для n элементов.  
- Бинарный поиск работает только с отсортированным массивом; без сортировки результат может быть неверным.  
- Оценка O(n) показывает рост затрат при увеличении размера входа, а не точное время выполнения.

Контракт функции требует проверки входных условий (непустой ввод, соблюдение лимитов) перед запуском.

Ответы сервера  
- При успешном выполнении запрос получает подтверждение.  
- Отказы бывают двух основных типов:  
  1. Превышение лимита запросов – сервер возвращает отказ (например, 429) или ставит запрос в очередь.  
  2. Ошибка на внутреннем этапе – клиент получает код ошибки и информацию для повторной попытки (текущий лимит, требуемый формат).

Методы запросов  
- GET — только чтение, состояние не меняет.  
- POST — создание ресурса или запуск действия (задания).

Коды ответов  
- 202 Accepted — задание принято, результат ещё не готов; клиент периодически запрашивает URL из заголовка Location.  
- 400 Bad Request — некорректный запрос.  
- 413 Payload Too Large — размер тела превышает допустимый.  
- 404 Not Found — ресурс не найден.  
- При ошибке внешнего сервиса возвращается понятное сообщение без деталей реализации.

Очередь заданий  
- Задания хранятся в порядке поступления, один исполнитель обрабатывает их последовательно.  
- Клиент получает идентификатор задания и может проверять статус: в очереди, выполняется, готово, ошибка.  
- Прогресс отражает количество завершённых частей, а не предполагаемое время окончания.  
- При ошибке частичный итог не отдается – результат считается недоступным.  
- Задания хранятся ограниченное время; после истечения срока они удаляются.  
- Если запросов больше лимита (например, 48 при лимите 30), сервер должен вернуть отказ или поставить их в ограниченную очередь, а не «потерять» запросы.

Повторные попытки  
- При отказе клиенту предоставляются код ошибки, заголовок Location (если есть) и рекомендация по интервалу повторения; секретные данные не включаются.

Таким образом, соблюдаются инварианты, проверяются граничные случаи, ограничения нагрузки и корректные коды ответов; измерения и асимптотика рассматриваются отдельно, а при ошибках клиент получает минимально необходимую информацию для повторного запроса.
