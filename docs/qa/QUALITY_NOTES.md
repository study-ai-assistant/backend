# Замечания по проверке

Дата: 26.11.2026. Исходники — `docs/demo`, ответы — `2026-11-26-live`.

## Сетевой таймаут

На коротком TXT в режиме KEY_TERMS одна попытка вернула 502 за 5,03 секунды.
Первый длинный TXT также завершился FAILED / LLM_TIMEOUT на первой части
примерно за шесть секунд. Оба сбоя сохранены в measurements.json.
В диагностике сервера: `reason=TIMEOUT, diagnostic=socket_timeout`.
Сервер оставался healthy; тело ответа соответствовало контракту и не содержало
служебных данных. Точную причину сети или стороны Groq по этим записям определить
нельзя. Эти сбои не доказывают ошибку backend и не скрывается при повторной проверке.
Скрипт остановился после ошибки; повторный прогон пропускает успешные сочетания
и начинает с паузы 61 секунду, чтобы не занять остаток минутной квоты.

Для записи видео: сначала проверить связь с Groq, не отправлять несколько
одинаковых запросов подряд при таймауте и оставить время на повтор сцены.

## Содержание ответов

HTTP 200 и SUCCEEDED сами по себе не подтверждают правильность учебного ответа.
Например, короткое SIMPLE_EXPLANATION содержит фразу «Если выполнить все шаги,
результат будет гарантирован». В исходнике такой гарантии нет: там сказано,
что алгоритм — конечная последовательность понятных шагов. Условия применимости
конкретного алгоритма всё равно нужно учитывать.

Это замечание к точности генерации, а не сбой API. Ответ оставлен без исправления.
Для конспекта, который студент будет использовать в учёбе, необходима проверка
по исходному материалу. Даже после уточнения промпта случайный ответ модели
может добавлять лишние утверждения.

Новые Issues и публикации автоматически не создавались: результаты этой работы
остаются локально в ветке. Если замечание к генерации принимается командой как
дефект, черновики карточек приведены в [BUG_DRAFTS.md](BUG_DRAFTS.md).

## Длинное простое объяснение: условия и числа

В `long-txt-SIMPLE_EXPLANATION.txt` обнаружены два искажения:

- Исходник допускает пустую коллекцию, если контракт явно её не запрещает.
  Ответ сначала сохраняет это условие, но ниже пишет, что контракт требует
  «непустой ввод». Получается внутреннее противоречие.
- В примере раздела 4 исходник связывает 48 запросов с ограничением 40.
  Ответ приводит «48 при лимите 30», смешивая числа из разных примеров.

Приоритет замечания — Medium: API завершает сценарий, но содержание ответа
требует исправления или ручной проверки. Промпты уже требуют сохранять условия
и связь чисел; одного наличия этой инструкции недостаточно для гарантии качества.
Черновик отдельной карточки — в BUG_DRAFTS.md. Сохранённый ответ не редактировался.

## Термины: определение квоты

В `long-txt-KEY_TERMS.txt` квота описана как ограничение, которое учитывает
и время ожидания, и число запросов за единицу времени. Исходник лишь отделяет
ожидание квоты от времени работы и не даёт такого определения. Модель связала
соседние упоминания в новое утверждение. Замечание Medium, отдельная карточка
подготовлена в BUG_DRAFTS.md. Для видео определение нужно сверять с исходником.
