# Тестирование backend

Полная проверка проекта:

```bash
./mvnw clean verify
```

Windows PowerShell:

```powershell
.\mvnw.cmd clean verify
```

Команда запускает Checkstyle, компиляцию, тесты и сборку JAR.
Отчёты находятся в `target/surefire-reports`. Сейчас проходят 94 теста.
Один тест проверяет таймаут LLM и ждёт около минуты, поэтому сборка может
некоторое время оставаться на `GroqLlmClientTests` без новых сообщений.

При первом запуске нужен интернет для загрузки Maven и зависимостей.
Сами тесты не обращаются к внешнему LLM и не требуют ключа. Тестовый сервер
использует свободный локальный порт; личный `.env` в HTTP-тестах не загружается.

## Что проверяется

- `BackendApplicationTests` — доступность сервера и списка режимов без ключа.
- `TextProcessingTests` — все пять JSON-режимов, проверка полей и лимитов, ошибка LLM.
- `MaterialProcessingTests` — загрузка TXT во всех режимах, UTF-8 и Windows-1251,
  BOM, пустые файлы, расширения, размер и длина текста, несколько файлов и ошибки.
- `GroqLlmClientTests` — запросы к локальному имитатору Groq, инструкции режимов,
  разбор ответа, ошибки провайдера и таймаут.
- `LlmPropertiesTests` — настройки LLM.
- `OpenApiContractTests` — корректность OpenAPI и ссылок на схемы.

Для запуска только HTTP-тестов обработки:

```bash
./mvnw -Dtest=MaterialProcessingTests,TextProcessingTests test
```

## Стиль кода и CI

```bash
./mvnw checkstyle:check
```

Правила находятся в `config/checkstyle/checkstyle.xml`: проверяются импорты,
табы, скобки, пустые statements и длина строк до 120 символов.

Workflow CI содержит задания `lint`, `tests` и `docker`. Они запускаются для PR
и push в main, feature, chore и docs. Тестовые отчёты сохраняются в артефактах;
задание docker собирает образ и проверяет `/health` и `/api/v1/modes`.
Настройку обязательных проверок в защите main выполняет администратор репозитория.

## Ручная проверка

Запустите сервер и выполните примеры из [инструкции API](../api/README.md).
Для реальной генерации нужны настройки Groq и ключ в `.env`.
Проверьте оба POST-маршрута, разные режимы и TXT в обеих кодировках.
Пустые данные должны давать 400, превышение лимита — 413, другой формат — 415.
Ошибка или таймаут провайдера возвращаются как 502.

JSON, TXT и Windows-1251 проверены с настоящим LLM. Ответы модели могут отличаться:
помимо статуса проверяйте смысл результата и сохранение фактов из исходника.

## PDF

PdfProcessingTests использует настоящие PDFBox и тестовые PDF, а LLM заменяет
заглушкой. Проверяются русский текст во всех режимах, порядок страниц,
сигнатура/расширение, сканы без текста, пароль, повреждение и лимиты страниц/текста.
PdfTextExtractorTests проверяет таймаут. Старые тесты TXT запускаются вместе с ними.

```bash
./mvnw -Dtest=PdfProcessingTests,PdfTextExtractorTests,MaterialProcessingTests test
```

Тестовые документы находятся в src/test/resources/pdf. Они созданы для проекта;
лицензия встроенного шрифта хранится рядом. Ключ LLM не нужен.

## Проверки ограничений PDF

PdfPropertiesTests проверяет привязку настроек и неверные значения.
PdfTextExtractorTests запускает процесс, который не обрабатывает прерывания,
проверяет его принудительное завершение, освобождение слота, ответ 503 при
занятом слоте и удаление файлов при ошибке запуска.

PdfProcessingTests проверяет каждый файл из тестового набора: русский текст,
несколько страниц, скан, таблицу, формулы, пароль и повреждение. Для успешных
файлов проверяется переданный текст, для ошибок — отсутствие вызовов LLM.
Отдельно проверяются размер, длина текста, лимит страниц из настроек, таймаут,
ошибка LLM и отсутствие содержимого в логах. После каждого HTTP-теста временная
папка должна быть пуста. Файлы и инструкция генерации — в
[описании набора](../../src/test/resources/pdf/README.md).

CI запускает эти тесты без ключа. Docker job дополнительно отправляет скан
в упакованное приложение и ожидает 422: это проверяет запуск PDF worker из JAR.
